# DIP worker boundary

Workers consume `document-jobs` from Redis and execute only the capabilities
declared by the Tool Registry. They must run separately from the web process
and use an isolated, resource-limited runtime for untrusted documents.

Each execution must persist its idempotency key, engine version, step status,
and terminal result before acknowledging queue work. Phase 1 introduces the
PDF worker implementation; this boundary deliberately contains no document
processing code.

## Phase 2 local server engine

The first Phase 2 delivery exposes a deliberately small server boundary at
`POST /api/tools/{word-to-pdf,pdf-to-word,excel-to-pdf,powerpoint-to-pdf,ocr-pdf}`. It creates a unique
temporary workspace per request, executes no shell strings, returns only the
generated bytes, and removes the workspace in all success and failure paths.

Install LibreOffice (`soffice`) for Office conversion and OCRmyPDF
(`ocrmypdf`) with Arabic/English Tesseract language data for OCR. Production
deployments should move this exact capability into the isolated worker runtime
described above, with storage and queue persistence, before public rollout.
