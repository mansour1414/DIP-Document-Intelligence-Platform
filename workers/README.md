# DIP worker boundary

Workers consume the BullMQ queue `dip.document-processing.v1` from Redis and execute only the capabilities
declared by the Tool Registry. They must run separately from the web process
and use an isolated, resource-limited runtime for untrusted documents.

Each execution must persist its idempotency key, engine version, step status,
and terminal result before acknowledging queue work. Phase 1 introduces the
PDF worker implementation; this boundary deliberately contains no document
processing code.

## Phase 2 local server engine (superseded by the worker pipeline)

The Phase 2 delivery originally exposed a synchronous server boundary at
`POST /api/tools/{word-to-pdf,pdf-to-word,excel-to-pdf,powerpoint-to-pdf,ocr-pdf}`,
which returned generated bytes directly and therefore bypassed the upload
malware boundary and the queue.

That route is now **fail-closed**. It retains only path resolution for the five
document tools and always responds:

```json
{ "code": "SYNC_PROCESSING_DISABLED", "message": "Synchronous processing is disabled for <tool>. ..." }
```

with HTTP `409` (HTTP `404` for any other tool id). It never imports or invokes
`processServerDocument()`, never creates a job record, and never writes to
storage. All Office/OCR work must go through `POST /api/jobs/[tool]`, which
applies `validateUpload -> requireCleanUpload -> storage.put` before enqueueing
to the document worker, with progress from `GET /api/jobs/status/[jobId]` and
authorized downloads from `GET /api/files/[fileId]`.

`GET /api/jobs/status/[jobId]` also returns `pollBudgetMs`, derived by
`jobPollBudgetMs()` from the configurable worker timeouts (engine timeout +
storage persist + queue grace, capped at 30 minutes). The browser polls at 1s
within that budget. If the budget ends while the job is still `QUEUED`,
`RUNNING` or `RETRYING`, the UI reports "still processing" and offers a
status re-check that resumes polling for the same job — it never marks a
running job as failed and never submits a duplicate job.

Client-side safety rules (see `src/lib/client/server-tool-job.ts`):

- A retained `Idempotency-Key` is bound to the submitted request: tool, option
  values, file name/size/lastModified and a per-selection token generated when
  the file is picked. This is **not** a content hash — the browser never hashes
  the file — but every new file selection (including one with identical
  metadata) and every option change yields a new key, so an ambiguous retry can
  never attach to a job that processed different options or different contents.
- An output download that fails after the job succeeded is retried up to three
  times for transient HTTP (5xx) and network (`fetch` TypeError) faults, then
  re-offered from the retained file id; authentication, authorization and abort
  failures are never retried. It never re-submits the document, so a transient
  storage or network fault cannot cause a second processing execution.
- `GET /api/jobs/status/[jobId]` and `GET /api/files/[fileId]` read through
  `src/lib/jobs/access.ts`, which runs the query inside `withTenant` (RLS
  context) **and** keeps the explicit owner predicate.

## Output screening (PR-1)

Generated outputs are malware-screened before they are published. The document
job body now lives in `src/lib/jobs/document-pipeline.ts` (the BullMQ worker is a
thin shell around it) and the order is fixed:

```
validateWorkerOutputs()  ->  screenWorkerOutputs()  ->  storeWorkerOutputs()  ->  metadata transaction
```

- **Every** output is scanned; one verdict never hides another. Scanning stops the
  job before the first object write, so a rejected batch leaves no object, no
  `File` row and no `SUCCEEDED` status behind.
- A batch is published only if **all** of its outputs return an explicit `CLEAN`.
  `INFECTED` on a single member rejects the whole batch, including its clean
  siblings.
- Scanner faults (`SCANNER_UNAVAILABLE`, `SCAN_ERROR`, `SCAN_TIMEOUT`) also fail
  closed. They stay retryable because the next attempt can succeed.
- `INFECTED` is deterministic (the same engines regenerate the same bytes), so it
  is escalated to a BullMQ `UnrecoverableError`: the job ends on the first
  attempt instead of re-running three times and re-alerting. The persisted job
  `errorCode` is still the precise `INFECTED` / `SCANNER_UNAVAILABLE` /
  `SCAN_ERROR` value.
- Storage writes are serial and compensating: a mid-batch write fault deletes the
  objects already written, and a failing metadata transaction deletes the
  objects it orphaned.
- Rejections record a content-free `security_events` row
  (`MALWARE_SCAN_REJECTED`, `source: "output"`) and the existing
  `malware_scan_total` / `worker_output_scan_rejected_total` metrics.
- Upload screening still requires `CLAMD_HOST`; the same fail-closed rule now
  applies to generated outputs, so a worker without a reachable scanner stores
  nothing.

### Effective rejection behaviour for very large outputs (unchanged limits)

`MALWARE_SCAN_MAX_BYTES` (100 MiB) is smaller than `MAX_OUTPUT_BYTES` (250 MiB),
and both approved values are **unchanged** by this work. The consequence,
documented rather than silently accepted: a single generated file larger than the
scan cap cannot be screened, so `requireCleanBytes()` fails closed and the job
ends `FAILED`. Today that surfaces as `SCAN_ERROR`, i.e. it looks like a scanner
fault rather than "output too large to scan".

Operational policy until a follow-up separates the code path (still without
changing either limit):

- treat **100 MiB per generated file** as the effective ceiling for the
  many-output tools (`pdf-to-jpg`, `extract-images`, split tools, large OCR
  PDFs) and publish that number in user-facing size-limit copy;
- alert on `worker_output_scan_rejected_total{status="scan_error"}` — a spike is
  more likely to be oversized outputs than a clamd outage;
- do **not** raise `MALWARE_SCAN_MAX_BYTES` / clamd `StreamMaxLength` ad hoc: they
  must move together and are an approved-limit change, not an operational one.

### Concurrent attempts of the same job (PR-1a)

BullMQ normally serialises a job, but stalled-job recovery can briefly run two
attempts of the same job id. Both are now harmless:

- **Attempt-scoped keys.** Outputs are written to
  `output/<userId>/<jobId>/<attemptId>/<index>-<name>`, so no attempt can ever
  overwrite another attempt's bytes.
- **Compare-and-set commit.** The `RUNNING` transition and the `SUCCEEDED` write
  are `updateMany` calls guarded on `outputFileId IS NULL` and a non-terminal
  status. Exactly one attempt can publish; the loser's document/file/version/
  `ToolExecution` rows are rolled back by Postgres, so duplicate successful
  metadata is impossible.
- **Safe cleanup ownership.** A losing or failing attempt deletes only the keys it
  wrote itself, and only when no committed `File` row references them
  (`worker.output_cleanup_skipped`). If ownership cannot be verified the objects
  are left behind (`worker.output_cleanup_unverified`): an orphan is recoverable,
  a deleted committed output is not.
- **No state rollback.** A losing attempt never marks a committed job `FAILED` or
  resets its step (`job.failure_suppressed`, `job.output_commit_superseded`,
  `job.terminal_skip`).
- **Orphan window.** An attempt killed between `put()` and commit (SIGKILL, no
  `finally`) leaves unreferenced objects under its own prefix. Add a bucket
  lifecycle rule (or a periodic sweep of `output/<user>/<job>/<attempt>/`
  prefixes with no `File` row) so they expire; they are never readable through
  the API because no row references them.

Install LibreOffice (`soffice`) for Office conversion. The approved OCR image uses
OCRmyPDF 17.10.0, pypdfium2 5.13.0 and Tesseract with Arabic/English data; it must
not contain a resolvable `gs` executable. Run `python scripts/verify-ocr-runtime.py`
as part of every approved OCR image build. These capabilities now execute in the
isolated worker runtime described above, with storage and queue persistence.

## Runtime processing (current)

`npm run worker:documents` starts the modular-monolith worker. It loads jobs using
the `Job → JobStep → ToolExecution` model, reads/writes only object keys in
S3-compatible storage, and emits structured `job_id` / `correlation_id` logs.
BullMQ retries three times with exponential backoff; output keys are scoped to the
attempt and the `SUCCEEDED` commit is a compare-and-set on `outputFileId`, so
retries and duplicate attempts cannot create duplicate output objects. Run
`npm run jobs:cleanup` from the platform scheduler to expire work older than 24h.
