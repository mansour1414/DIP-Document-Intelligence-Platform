# DIP worker boundary

Workers consume the BullMQ queue `dip.document-processing.v1` from Redis and execute only the capabilities
declared by the Tool Registry. They must run separately from the web process
and use an isolated, resource-limited runtime for untrusted documents.

Each execution must persist its idempotency key, engine version, step status,
and terminal result before acknowledging queue work. Phase 1 introduces the
PDF worker implementation; this boundary deliberately contains no document
processing code.

## Phase 2 local server engine (superseded by the worker pipeline)

The Phase 2 delivery originally exposed a synchronous server boundary at
`POST /api/tools/{word-to-pdf,pdf-to-word,excel-to-pdf,powerpoint-to-pdf,ocr-pdf}`,
which returned generated bytes directly and therefore bypassed the upload
malware boundary and the queue.

That route is now **fail-closed**. It retains only path resolution for the five
document tools and always responds:

```json
{ "code": "SYNC_PROCESSING_DISABLED", "message": "Synchronous processing is disabled for <tool>. ..." }
```

with HTTP `409` (HTTP `404` for any other tool id). It never imports or invokes
`processServerDocument()`, never creates a job record, and never writes to
storage. All Office/OCR work must go through `POST /api/jobs/[tool]`, which
applies `validateUpload -> requireCleanUpload -> storage.put` before enqueueing
to the document worker, with progress from `GET /api/jobs/status/[jobId]` and
authorized downloads from `GET /api/files/[fileId]`.

`GET /api/jobs/status/[jobId]` also returns `pollBudgetMs`, derived by
`jobPollBudgetMs()` from the configurable worker timeouts (engine timeout +
storage persist + queue grace, capped at 30 minutes). The browser polls at 1s
within that budget. If the budget ends while the job is still `QUEUED`,
`RUNNING` or `RETRYING`, the UI reports "still processing" and offers a
status re-check that resumes polling for the same job — it never marks a
running job as failed and never submits a duplicate job.

Client-side safety rules (see `src/lib/client/server-tool-job.ts`):

- A retained `Idempotency-Key` is bound to the exact submitted request
  (tool, file name/size/lastModified and options). Changing the OCR language or
  the file is a new operation and is submitted under a new key, so an ambiguous
  retry can never attach to a job that processed different options.
- An output download that fails after the job succeeded is retried up to three
  times and then re-offered from the retained file id; it never re-submits the
  document, so a transient storage or network fault cannot cause a second
  processing execution.
- `GET /api/jobs/status/[jobId]` and `GET /api/files/[fileId]` read through
  `src/lib/jobs/access.ts`, which runs the query inside `withTenant` (RLS
  context) **and** keeps the explicit owner predicate.

Install LibreOffice (`soffice`) for Office conversion. The approved OCR image uses
OCRmyPDF 17.10.0, pypdfium2 5.13.0 and Tesseract with Arabic/English data; it must
not contain a resolvable `gs` executable. Run `python scripts/verify-ocr-runtime.py`
as part of every approved OCR image build. These capabilities now execute in the
isolated worker runtime described above, with storage and queue persistence.

## Runtime processing (current)

`npm run worker:documents` starts the modular-monolith worker. It loads jobs using
the `Job → JobStep → ToolExecution` model, reads/writes only object keys in
S3-compatible storage, and emits structured `job_id` / `correlation_id` logs.
BullMQ retries three times with exponential backoff; a stable output key based on
the job id means retries cannot create duplicate output objects. Run
`npm run jobs:cleanup` from the platform scheduler to expire work older than 24h.
