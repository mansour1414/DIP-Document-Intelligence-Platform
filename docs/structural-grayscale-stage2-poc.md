# DIP Structural Grayscale Engine — Stage 2 PoC

## Decision and scope

**Status: isolated PoC passed for the bounded supported subset; production adoption is not approved. Phase 1 remains NOT COMPLETE.**

This experiment extends the DIP-owned token-level transformer from Stage 1. It is not connected to the Tool Registry, Job/Worker, Workflow, Agent, Public API, UI, or production image. It does not flatten or rasterize pages and it does not use MuPDF, PyMuPDF, or Ghostscript. The implementation follows the PDF object/content-stream model in ISO 32000-1 and uses pikepdf only as an experimental parser/writer and token-filter host.

## Experimental implementation

The isolated implementation is `scripts/experiments/structural-grayscale-stage2.py`; its exact QA environment is pinned in `scripts/experiments/structural-grayscale-stage2.requirements.txt`.

The engine is divided into these bounded modules:

1. **Preflight:** rejects oversized, encrypted, signed, malformed, and over-complex inputs before mutation.
2. **Color resolution:** resolves page/Form/Pattern resource dictionaries and implements a documented conversion policy for Device, calibrated, ICCBased, and Indexed spaces.
3. **Content filtering:** rewrites only color-setting operands/operators while preserving unrelated operators and operands.
4. **Image conversion:** decodes only the explicitly supported image subset, converts pixels through the declared color policy, and writes a bounded DeviceGray/Flate image.
5. **Object-graph traversal:** recursively processes nested Form XObjects, shared resources, transparency soft-mask groups, appearances, patterns, and shadings with object deduplication and active-stack cycle detection.
6. **Forms/annotations:** processes widget `/AP/N`, `/AP/R`, and `/AP/D`, including appearance-state dictionaries; converts `/MK` background/border colors and `/DA` strings without generating arbitrary appearances.
7. **Validation:** reopens the output, checks syntax, scans supported streams/resources/images for residual color, compares document semantics, renders independently with PDFium, and verifies field editing behavior.

### Explicit color-management policy

- DeviceRGB is treated as sRGB, converted through linear-light relative luminance, then encoded as sRGB gray.
- DeviceCMYK content operators use the PoC's explicit simple subtractive fallback. This is deterministic but is not a proof of press-quality colorimetry.
- CalGray uses the declared white point and gamma after validating the dictionary.
- CalRGB is supported only for the proven D65/gamma/matrix subset; it is converted through XYZ to sRGB and then to gray.
- ICCBased RGB and CMYK images are transformed to sRGB with Pillow's LittleCMS binding and then to gray. Invalid or unsupported profiles fail closed.
- Indexed color spaces are supported only with a bounded palette and a supported base space.
- Unprofiled CMYK images are rejected instead of applying an unproved image policy.

## Security and resource results

The experiment enforces these internal ceilings: 4 MB input, 8 MB output, 8 MB aggregate decoded streams, 2 MB per decoded stream, 1,000,000 pixels per image, 50 images, 2,000 objects, 400 streams, 10 pages, recursion depth 20, and a 15-second transformation wall-clock budget. Temporary work is isolated and the self-test verifies cleanup.

The following probes failed closed as intended:

- unsupported image filter;
- cyclic Form graph;
- signed input;
- encrypted input;
- malformed input;
- unsupported spot color.

These are in-process PoC guards. Production CPU/RAM/process/tmpfs enforcement, malware scanning, tenant/job binding, cancellation, structured observability, and sandbox behavior were not changed or requalified. A production gate must repeat the corpus under the actual non-root, read-only-root, bounded-tmpfs worker and apply an external hard timeout/memory limit.

## Supported subset

- DeviceGray, DeviceRGB, and DeviceCMYK content operators.
- Valid bounded CalGray and the tested D65 CalRGB subset.
- Valid ICCBased RGB/CMYK image profiles through LittleCMS.
- Bounded Indexed palettes over a supported base color space.
- Unfiltered or Flate 8-bit DeviceRGB/DeviceGray Image XObjects and inline images.
- DeviceGray soft masks; transparency dictionaries are preserved.
- Nested Form XObjects, shared resources, and soft-mask groups with cycle detection.
- Colored tiling patterns (`PaintType 1`) in the tested subset.
- Axial (`ShadingType 2`) shadings with one Type 2 function in the tested subset.
- Widget direct and state-dictionary `/AP/N`, `/AP/R`, `/AP/D`, `/MK`, and `/DA`.

## Unsupported features (mandatory rejection)

- DCT/JPEG, JPX, JBIG2, CCITT, and other non-Flate image filters.
- Unprofiled CMYK images.
- Separation, DeviceN, Lab, and uncolored patterns.
- Radial/mesh shadings, stitching/multi-function shadings, and other unproved function types.
- Non-gray explicit masks and unsupported transparency/color-space combinations.
- XFA, JavaScript-generated appearances, signatures, encrypted inputs, and arbitrary appearance regeneration.
- Guarantees about appearance regeneration in external viewers.

The engine does not silently preserve, flatten, remove, or rasterize these cases. It rejects the entire document.

The exact isolated environment was:

The Windows pikepdf wheel contains native `_core.pyd`, a bundled `qpdf30` DLL, and an MSVC runtime. Pillow contains `_imagingcms.pyd`; lxml, pypdfium2, and uharfbuzz also contain native binaries. The inspected Windows pikepdf wheel did not include a CycloneDX SBOM. Pikepdf's wheel documentation says Linux wheels include one, but that must be verified against the exact target Linux wheel and production image rather than assumed.

The production worker currently obtains pikepdf indirectly through OCRmyPDF's broad dependency constraint. That neither pins the exact version nor approves direct application use. Stage 2 added no package to `package.json`, Python production requirements, Dockerfile, worker image, or license registry. Before adoption, the owner must approve a direct exact dependency, MPL file-level obligations/notices, the embedded libqpdf divergence, LittleCMS/native runtime chain, and a generated production SBOM.

## Comparison with Stage 1

Stage 1 proved simple DeviceRGB/DeviceCMYK page operators and one direct normal widget appearance. Stage 2 experimentally adds supported images and inline images, calibrated/ICCBased/Indexed policy, recursive/shared Forms, cycle rejection, all three widget appearance categories and state dictionaries, non-regenerating field edits, transparency/soft masks, one pattern subset, and one shading subset. It also adds independent PDFium rendering and a larger fail-closed corpus.

Stage 2 does **not** turn the PoC into a generally complete PDF color engine. The remaining format surface and deployment/security evidence are material acceptance blockers.

## Next proposed acceptance gate

Owner approval is required before a Stage 3 production-readiness experiment. That gate should require all of the following:

1. Approve and pin direct Linux pikepdf/Pillow/LittleCMS versions, licenses, native artifacts, notices, and SBOM; reconcile embedded libqpdf 12.3.2 with the separately approved qpdf 11.3.0 CLI.
2. Establish a logical-order Arabic fixture generated independently of the engine and verify search/copy in multiple readers.
3. Decide whether the current reject-only subset is product-acceptable or fund additional safe support for common JPEG/JPX images, unprofiled CMYK, Lab/spot colors, additional patterns/shadings/functions, and complex masks.
4. Run real-world, hostile, malformed, incremental-update, XFA, signed, and encrypted corpora under the actual production worker sandbox with hard CPU/RAM/tmp/process/output limits and fuzzing.
5. Prove appearance behavior across supported viewers and field editors, including explicit product policy for any component that regenerates appearances.
6. Add production architecture/UI/API integration only after the above gates pass and a separate Change Request is approved.

Until then, Grayscale remains a **CAPABILITY/PoC BLOCKER** and **CHANGE REQUEST REQUIRED** item. No production claim or Phase 1 completion claim is justified.
