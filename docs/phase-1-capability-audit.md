# Phase 1 capability and security gates

This record applies to the remaining Page & Security tools and does not change the MASTER BASELINE.

## Completed with the approved JavaScript stack

- Split PDF by Size uses `pdf-lib` serialization to form deterministic page groups. The target is explicitly approximate; a single page may exceed it. Every part is reopened by the common output validator.
- Split PDF by Bookmarks accepts direct internal page destinations only. Nested items, duplicate titles, and Unicode titles are supported. Named, missing, invalid, cyclic, remote, and external destinations fail closed. Document-level data is not claimed to survive the split.
- Split PDF by Text uses PDF.js text extraction and literal substring matching only. A matching page starts a new part. Multiple matches on one page create one boundary; no match fails. Case sensitivity is explicit. No regex, AI, or implicit OCR is used.
- N-up PDF composes 2/4/6/9 pages with `pdf-lib`. It preserves visible page content and geometry but intentionally does not claim preservation of interactive links, forms, or annotations.
- Remove Annotations uses an explicit subtype allowlist. Form widgets are retained. Link removal requires the `comments-and-links` policy. PDFs containing signature fields or `ByteRange` signatures are rejected because rewriting may invalidate integrity.

## Grayscale quality PoC — CAPABILITY/PoC BLOCKER

The approved stack can rasterize pages, but reconstruction from rendered pixels removes searchable text, vector objects, links, forms, and other document semantics. `pdf-lib` 1.17.1 has no supported content-stream/color-space transformation API that can reliably convert arbitrary PDF color operators, embedded images, transparency groups, patterns, shadings, and ICC color spaces while preserving those semantics. PDF.js is a display/parser path, qpdf deliberately does not interpret content-stream semantics, and the approved PDFium path is a renderer rather than a proven semantic rewrite path. Shipping rasterization as ordinary grayscale success would violate the approved quality requirement.

An isolated PoC evaluated PyMuPDF/MuPDF 1.28.2 without adding it to the application or worker. `Document.recolor(1)` preserved page count/order/geometry, searchable English and Arabic text, links, text annotations, AcroForm field identity/value/type, outlines, metadata, images, vector objects, and transparency in the fixture. It converted RGB and CMYK page content, an embedded RGB image with an sRGB ICC profile to a gray ICC profile, and rendered page content to equal gray channels. A 50-page repeat fixture reopened successfully with all text present. A truncated PDF was rejected and an encrypted PDF required authentication.

The same PoC also produced a mandatory acceptance failure: a colored AcroForm widget appearance stream remained colored. The output rendered with annotations/widgets had a maximum RGB channel delta of 204 across 24,888 pixels on the affected page, while rendering the same page with annotations disabled had a zero channel delta. Regenerating or replacing form appearance streams can alter custom fonts, layout, scripts, signatures, and author-supplied appearances, so it is not accepted as a safe automatic repair. Signed inputs must also be rejected because any recolor rewrite invalidates the signed byte ranges; encrypted inputs remain outside this non-secret tool path.

PyMuPDF 1.28.2 has no declared Python package dependencies but ships native MuPDF binaries in-process. It is dual-licensed under AGPL-3.0 or an Artifex commercial license. The AGPL build is not approved for DIP's proprietary hosted deployment, and no commercial license or SBOM approval has been recorded. Adobe PDF Library documents a broader commercial color-conversion API, but it is licensed case by case, introduces native runtime dependencies, and has not yet proven annotation/form appearance handling against the DIP corpus.

Therefore no implementation, dependency, registry entry, UI page, workflow/agent exposure, or public API contract was added. Production implementation requires an approved product and licensing Change Request selecting a commercially permitted semantic conversion engine and defining safe behavior for form/widget appearance streams. Rasterization remains explicitly rejected.

An independent follow-up PoC demonstrated that pikepdf can structurally enumerate and replace direct and state-dictionary widget `/AP/N`, `/AP/R`, and `/AP/D` Forms after recoloring each appearance through an isolated MuPDF carrier page. Converting `/MK` colors and `/DA` color operators also prevented the tested field-value regeneration path from reintroducing color. The synthetic output rendered with zero colored pixels and retained its tested semantics. This resolves the narrow technical root cause in the fixture, but not the production gate: semantic recoloring still depends on commercially unapproved MuPDF, pikepdf direct use is not approved or pinned, its wheel embeds libqpdf 12.3.2 rather than the approved qpdf 11.3.0 CLI, and the required real-world/hostile/XFA/signed/multi-viewer corpus has not passed. See `docs/grayscale-independent-poc.md`.

A subsequent DIP-owned Stage 1 experiment removed MuPDF entirely and used pikepdf's token-filter API to convert only simple DeviceRGB/DeviceCMYK page operators and one text widget's direct normal appearance, `/MK`, and `/DA`. Its transformed render was pixel-identical to an independently generated expected fixture; searchable text and the field name/type/value were unchanged, and unsupported color-space, signed, encrypted, and malformed probes failed closed. This is a useful foundation, not a production implementation: images, ICC, patterns, shadings, transparency, nested Forms, general appearances, field regeneration, hostile corpora, and hard production resource enforcement remain unresolved. No application dependency, registry entry, route, worker, or API was changed. See `docs/structural-grayscale-stage1-poc.md`.

Stage 2 extended that independent engine in isolation to a deliberately bounded subset covering Flate/unfiltered images and inline images, calibrated/ICCBased/Indexed color policies, nested/shared Forms with cycle rejection, widget `/AP/N`, `/AP/R`, and `/AP/D` state dictionaries, `/MK` and `/DA`, a non-regenerating field-edit path, transparency/soft masks, one colored-pattern subset, and one axial-shading subset. The English and Arabic fixtures retained their tested text/field/link snapshots, reopened without syntax warnings, and rendered with zero colored pixels; the render MAE against independently generated grayscale fixtures was 0.060903. Unsupported filters, spot colors, cycles, signed, encrypted, and malformed inputs failed closed. Production remains blocked: common image/filter/color features are intentionally rejected, logical-order Arabic extraction is not independently proven, external appearance regeneration is unproved, hard worker limits/fuzzing are pending, and direct pikepdf/Pillow/LittleCMS adoption plus its native/SBOM chain is not approved. No production dependency or interface was changed. See `docs/structural-grayscale-stage2-poc.md`.

Stage 3A added an isolated single-filter DCT/JPEG path, explicit Lab content, a bounded Separation/Type 2 tint subset, explicitly profiled ICCBased CMYK content, radial Type 3 shading, an independently generated Chromium Arabic fixture, three-reader text checks, and a pypdf appearance-regeneration path. The structural output preserved its tested semantics and rendered with zero chroma. The remaining visual error was confined to the deliberately lossy JPEG region (whole-page MAE 0.008362, maximum delta 6); Lab, Separation, ICCBased CMYK, radial shading, and the corrected Stage 2 inline expected region were pixel-identical. Eleven unsupported/security probes failed closed. The logical-order Arabic gate remains failed because PDFium returns the independent fixture in visual RTL order even though pypdf and PDF.js find the logical phrase. Exact CPython 3.11 Linux-wheel inspection also found an incomplete pikepdf SBOM for bundled libqpdf and a Pillow SBOM entry for GPL-3.0-or-later libimagequant that requires linkage/obligation review. No production dependency or interface changed. See `docs/structural-grayscale-stage3a-poc.md`.

## Extract Images PoC — supported subset implemented

PDF.js 6.3.289 operator data supports a useful, bounded subset: decoded image XObjects exposed as 1-bit grayscale, RGB, or RGBA pixel buffers. DIP exports those objects as PNG, deduplicates identical decoded pixels, and emits an explicit JSON capability report. It does not claim byte-identical original streams and never substitutes rendered page screenshots. Inline images and objects that PDF.js does not expose as a bounded supported pixel buffer are counted as unsupported. Per-image dimensions/pixels, output count, and total bytes are bounded before persistence.

## qpdf security gate — implemented; production CI verification required

- The worker package is pinned to Debian `qpdf=11.3.0-1+deb12u1`; the build checks the installed Debian package version.
- The production-image CI gate runs qpdf as UID/GID 10001 under a read-only root filesystem and bounded `/tmp/dip` tmpfs. It verifies the exact executable/package version, AES-256/R6, correct and wrong credentials, Arabic/Unicode credentials, permission mappings, recoverable and unrecoverable repair cases, and Ghostscript absence.
- Passwords are AES-256-GCM encrypted in short-lived Redis records referenced by opaque IDs bound through authenticated additional data to tenant, job, and purpose. Retrieval is one-time. Success, failure, cancellation, and TTL expiration all remove or expire the record. Only the opaque reference is persisted; BullMQ continues to carry only job identity and routing metadata.
- qpdf receives one private mode-0600 argument file by `@file`; the process argument array never contains a password and `shell` is disabled. The private mode-0700 directory is removed in `finally`.
- Protect, Unlock, PDF Permissions, and Repair are registered for direct Web/Public API and the worker. The three secret-bearing tools are deliberately rejected by persisted Workflows and excluded from Agent plans. Repair requires no secret and remains available where policy permits.
- This local host has neither qpdf nor Docker. The gate is implemented but its production-image result remains environment-gated until the extended GitHub job runs successfully.

## Architecture result

The existing output manifest already supports multiple `outputFileIds`; no contract redesign or ZIP dependency was required. No new package, AI path, or Ghostscript path was introduced. qpdf is invoked only through the already approved pinned production package and the controlled argument-file wrapper.
Stage 3B experimentally confirmed that PDFium's Arabic visual-order behavior is present identically before and after grayscale transformation, generated a supplemental libqpdf SBOM inventory, proved the exact Pillow 12.3.0 Linux wheel does not bundle/link/use libimagequant on the tested path, and passed a nine-JPEG/two-renderer corpus plus bounded mutation probes. Production sandbox execution and Unicode widget-appearance fidelity remain gated; see `docs/structural-grayscale-stage3b-readiness.md`.

Stage 3C adds an isolated fail-closed GitHub Actions job that builds the unchanged production worker and a derivative, pins and hashes the experimental Linux wheels, verifies native ELF/SBOM inventory, and requires UID/GID 10001, read-only root, disabled processing network, cgroup/ulimit bounds, bounded tmpfs, cleanup, and Ghostscript absence. A new Unicode-capable Arabic/mixed widget corpus preserved field semantics and all appearance states; transformed, grayscale-aware edited, and reprocessed renders were pixel-identical to independently generated grayscale fixtures. The job is implemented but has not run from this uncommitted tree, so Linux sandbox proof remains environment-gated and production adoption remains unapproved. See `docs/structural-grayscale-stage3c-ci-gate.md`.
